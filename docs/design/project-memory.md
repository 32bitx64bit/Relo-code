# Cross-session project memory

Status: proposal for review. This document changes no implementation. Paths are repository-relative. Requirements below are design decisions, not claims about current behavior or measured performance.

## 1. Outcome and existing architecture

Relo should remember useful, verified project facts, recurring pitfalls and tool-loop lessons, working commands, and durable decisions across sessions. The Primary (head) alone decides whether an agent-proposed entry is useful enough for permanent memory. Workers, probes, imported content, and agent-side RPC callers may propose or request review, never promote directly. The user outranks the head: direct user actions through the Memory UI (`memory.update`, `memory.delete`, `context.promote` with user provenance) apply immediately and need no head gate. Rationale: a UI edit can occur with no live session and therefore no head turn to approve it, and the user owns the project memory the head merely curates. Permanent means retained until explicitly retired or deleted, not unconditionally true forever.

Existing code, inspected in this repository:

- `core/internal/memory/store.go`: `Entry`, `Store.Upsert`, `Retrieve`, `Recall`, `Delete`, `Bound` (200), `RecallLimit` (4), `RecallChars` (600), and `trim`. `Upsert` deduplicates by normalized kind and title; `trim` can evict even verified entries when all are verified. `Recall` matches distinctive words; it has no commit or hash validity check.
- `core/internal/orchestrator/worker.go` writes compressed worker reports via `c.Memory.Upsert`; completed non-probe reports without failed checks receive `Verified=true`. `session.go` and `worker.go` recall into `ctxeng.ClassMemory`; `facts.go` defines `staleMemory`. The head's `Turn` and worker's `RawReport` live in `orchestrator/parse.go`; `session.go` has `applyDecisions`, `setConstraints`, and `answerEvidence`. `prompt/prompt.go` specifies structured output. `context/engine.go` renders context, while `context/tokens.go` supplies `Tokens`, an estimate using rune count divided by four by default, not a provider-token guarantee.
- `app/app.go` handles `context.promote`, `memory.list`, `memory.update`, `memory.delete`, `memFrom`, and `memFromParams`; it persists each memory entry in `persistLocked` and restores via `Upsert`. `persistence/catalog.go:migrateCatalog` defines catalog `memory(id,workspace,payload,updated_at)`; `persistence/store.go:Open`, `PutJSON`, and `List` route it to the catalog. Default location is `<workspace>/.relo/catalog.db` (`app/app.go`); configured DB paths select their containing directory. Current in-memory mutex and full-snapshot writes do not coordinate separate processes.
- `orchestrator/coord.go` has `Settings.Memory` (`projectMemory`, default true); `app/app.go:applySettings`, `extension/src/extension.ts`, and `extension/package.json` wire `relo.context.projectMemory`. `extension/src/protocol.ts` includes the current memory RPC names, snapshot memory and a no-op `memory.updated` reducer. `webview/src/main.js:drawerRowsContext` displays context agents; its settings section exposes the existing flag, but it has no memory review UI. `docs/protocol.md` lists RPCs and notifications.

## 2. Reference comparison

Reference source is [microsoft/TokenEconomizer](https://github.com/microsoft/TokenEconomizer), particularly `README.md`, `tokeneconomizer/microskills/envfacts.py`, `stage.py`, `lifecycle.py`, and `plugin/fold.py`. Source and documentation only; do not install or run it. Probe findings characterize its micro-skills, not necessarily every other plugin feature. Upstream may change; pin a commit before implementation benchmarking.

| Dimension | TokenEconomizer reference | Proposed Relo improvement, checkable acceptance |
|---|---|---|
| Scope | Environment facts including repairs, boundaries, empty probes and argument repairs | Four typed entry families include code facts, tool loops, commands and explicit decisions; tests cover each. |
| Promotion | `K_PROMOTE=3`; firing also has an evidence gate | Head can promote one independently verified, provenance-bearing candidate immediately; no time/session-count threshold. An unsupported claim never promotes. |
| Retrieval | `PrefixStage.render` emits a capped session-start block, at most 4 facts/150 tokens; no semantic task query | Each prompt selects by current task, explicit paths and symbols, with a 300 estimated-token total cap and 4-entry maximum. Unrelated entries are omitted. |
| Validity | Confirmation/contradiction decay and retirement | Recheck evidence commit ancestry and content hashes against each recipient's actual view before every recall; changed evidence never enters as current verified memory. |
| Durability | Active items can decay or retire | Head-approved entries survive capacity trimming and ordinary restarts; stale items remain reviewable but excluded from ordinary recall. |
| Review/control | Plugin's local learned state and reversible behavior | User sees provenance, status, edits, retire/delete and flagged agent contradictions in existing Context surface; user edits apply directly with `source: user` provenance and need no head approval. |
| Isolation | Repository/host-scoped local state | Existing workspace catalog partition is retained; no cross-workspace sharing or implicit global transfer. |

TokenEconomizer's README reports benchmark savings; those results do not establish Relo savings. This design makes no measured cost or quality claim. Test useful recall, task success and total input tokens including added head review before claiming improvement.

## 3. Entry, evidence and lifecycle

Extend `memory.Entry` JSON in the existing catalog; use `schemaVersion: 2`. All strings and lists have explicit size limits and pass the intake policy in §7 before any persistence or output. Example is illustrative; paths and hashes are placeholders:

```json
{
  "schemaVersion": 2, "id": "mem_example", "revision": 3,
  "kind": "command", "state": "verified", "title": "Run core tests",
  "body": "Run go test from the core module directory.",
  "command": {"argv": ["go", "test", "./..."], "cwd": "core", "environment": "local Go toolchain"},
  "scope": {"workspace": "canonical-workspace-id", "paths": ["core/go.mod"], "symbols": [], "tags": ["tests"]},
  "evidence": [{"type": "command_result", "sessionId": "session_example", "agentId": "agent_example", "ref": "evidence_example", "observedAt": "2026-01-01T00:00:00Z", "commit": "git-oid", "files": [{"path": "core/go.mod", "sha256": "sha256-hex"}], "result": "passed"}],
  "promotion": {"headTurnId": "turn_example", "rationale": "Useful for core changes", "promotedAt": "2026-01-01T00:00:00Z"},
  "source": "head",
  "created": "2026-01-01T00:00:00Z", "updated": "2026-01-01T00:00:00Z"
}
```

Types: `fact` is an observable project property; `pitfall` describes a specific failure/loop, trigger, and verified alternative or safe stop; `command` records argv, relative cwd, non-secret environment description, expected result and relevant prerequisites; `decision` cites an explicit user decision or accepted durable project artifact. Free-form shell text is display-only. Evidence is references plus sanitized metadata, never transcripts, output snippets, credentials, email, or raw environment variables. References must resolve to durable local evidence records; a missing/deleted record makes the entry ineligible until reverified. Do not infer user authorization from head or worker text. A user decision counts as evidence only when a trusted local user-message record actually supports it.

Each evidence record includes type (`file_observation`, `command_result`, `user_decision`, or `accepted_artifact`), session/agent IDs, resolvable local record ID, observation time, observed git commit when available, relevant workspace-relative paths with SHA-256 of bytes actually inspected, and an outcome. `command_result` must refer to a recorded command execution and exit status, not just a model's report that it passed. Evidence must be relevant to the exact claim, not merely present. A failed command may prove a pitfall; a working alternative requires separate successful evidence. A proposal with unresolvable evidence stays candidate. Hashes are integrity anchors, not proof that a claim is true. Evidence outside the repository requires a bounded environment descriptor and a review deadline; no free-form external secrets.

States:

1. `candidate`: created by an agent-originated write only — a worker report, a head proposal, or `memory.propose`; non-permanent and never injected as fact. User direct writes never create candidates (§4). Retain at most 200 candidates per workspace, evict oldest candidates only; 30-day expiry. No automatic promotion on completed reports, score, model assertion, number of sessions, or user click.
2. `verified`: permanent entry. Agent-originated material becomes verified only after the current head turn names candidate ID, expected revision, evidence references and usefulness rationale. Core validates provenance, scope, safety, and freshness, then commits promotion atomically. Head judges claim support and usefulness; core checks the references and recorded outcomes exist and match the submitted claim's cited material, not that arbitrary natural language is logically entailed. One supported observation can suffice. A hypothesis, failed/unrun verification presented as success, unverifiable decision, stale evidence or rejected safety check cannot promote. The head gate covers agent-originated writes only; a direct user write (§4) reaches `verified` without a head turn.
3. `stale`: permanent but excluded from normal recall. Global contradiction or expiry marks it stale; view-specific git/hash mismatch is computed per recipient without globally mutating the entry, since parallel branches can differ. Reverification creates new evidence and requires another head promotion; no silent return to verified.
4. `retired`: permanent historical record deliberately withdrawn by head or user, excluded from recall. A new candidate is required to reinstate an agent-originated entry; a user may reinstate a user-provenance entry with another direct write. Explicit delete removes the entry payload and associated memory-only data from active tables and replaces the row with a content-free tombstone; deletion is different from retirement. SQLite pages, WAL and backups need separate secure-erasure handling (§6).

Verified entries have no automatic capacity eviction. On a configured quota or storage failure, reject promotion visibly; never evict permanent entries. Same-title reports never merge into a verified entry: new material is a distinct candidate linked by `supersedesId`; promotion and supersession require revision checks. Keep one active claim per explicitly linked replacement, never infer equivalence from title alone. `created`, `updated`, `revision`, `state`, evidence and promotion metadata are server-controlled. Agent edits create a new candidate and leave the old entry unchanged until the head promotes its replacement; a user may immediately retire the old entry. A direct user edit instead commits in place under revision check with `source: user` provenance; a targeted verified entry of user provenance can be edited only by the user.

## 4. Capture, review and head gate

Extend `RawReport`/`agent.Report` with optional bounded `memoryProposals` containing structured fields and evidence references. `worker.go` turns them into candidates only; existing generic compressed report capture must stop producing verified entries. Probe reports may propose but never self-certify. `session.go` collects candidate IDs into a bounded head review queue with evidence summaries, never raw transcript text. Extend `Turn` and `prompt/prompt.go` with `memoryDecisions` (`candidateId`, `revision`, `action: promote|reject|defer`, `evidenceRefs`, `rationale`). Head decisions apply only to candidates presented to that specific live head turn; core checks turn identity, candidate revision, exact evidence and safety before committing. `reject` retires the candidate; `defer` leaves it. Invalid or replayed decisions fail closed and are surfaced to the head/user. No extra model call is required: use the next ordinary head turn; pending proposals survive restart. No promotion occurs if there is no head turn.

`applyDecisions` and `setConstraints` remain session context, not automatic permanent decisions. A project decision requires a separate candidate citing actual user text or an accepted artifact, and head review. A user request to promote an agent-proposed entry supplies a candidate/review request only; it cannot assert `verified`, promotion metadata, evidence result or head identity.

Direct user writes are a separate, privileged path and never candidates. `memory.update`, `memory.delete` and `context.promote` issued from the Memory UI act on behalf of the user and apply immediately: no candidate state, no review request, no head turn, no wait for a session. Rationale: the user outranks the head, and a UI edit can occur with no live session at all, so requiring approval would leave the write pending with no possible approver. Rules for that path:

- Provenance records `source: "user"` with the event actor, commit time and resulting `revision`; core fills these, and a caller-supplied value is ignored.
- The same intake policy (§7) runs first: a payload that trips the secret/email pattern scan is rejected with `unsafe_content` and never stored, even for the user. Rejecting on a hit is not a review state.
- The write is versioned: it requires the expected `revision` and commits atomically.
- `memory.delete` leaves a content-free tombstone (§6) and never keeps the payload.
- `context.promote` promotes the named `itemId` directly as a verified user-provenance entry.

Head approval gates agent-originated writes only: worker/head proposals and `memory.propose` still require the head turn. Agents can never overwrite, retire or downgrade a user-provenance entry; when an agent proposal, a worker observation or a per-view staleness check contradicts one, the contradiction becomes a flagged candidate for user review and the user entry stays in effect. `answerEvidence` is a useful precedent for verifying cited user text, not a sufficient verifier for arbitrary memory evidence.

Evidence references must be created by trusted runtime/persistence adapters from observed file reads, command results or accepted artifacts, with immutable reference IDs and sanitized metadata. Where Relo cannot reliably establish an observation, do not fabricate it: proposal stays candidate. No reading raw historical reports as automatically trustworthy evidence. Evidence must refer to the exact worktree view and inspected file bytes, not merely the main workspace. Avoid copying complete command output or user messages into the memory store.

## 5. Staleness and retrieval

At capture record the evidence commit and hashes from the agent's actual view, including dirty bytes. Restrict paths to normalized relative paths within the workspace; reject absolute paths, `..`, `.git`, `.relo`, escaping symlinks and non-regular files. Resolve safely at read time as well. Hash files without following an escaping symlink. Absence or read failure makes that evidence stale. Record verified absence explicitly with an absence marker when an empty probe is the claim; existence later invalidates it.

At each head or worker prompt, evaluate against that recipient's actual workspace/worktree snapshot, including uncommitted on-disk edits. Evidence is current only if every referenced path matches its SHA-256/absence marker and its commit is the current commit or a git ancestor. Unavailable git/unknown commit/ancestry failure is unknown, not valid; a rebased but byte-identical tree requires re-verification. Changes in unrelated files do not stale a record. If a view cannot account for unsaved editor buffers, suppress affected evidence or fail closed for the view; do not claim disk hashes represent unsaved text. Environment/command facts additionally expire 30 days after observation or on known toolchain/environment fingerprint mismatch; fingerprints contain only safe identifiers/versions, no environment variable values. Verified contradictions mark the global record stale; unverified counterclaims only enqueue review. A user-provenance entry is never auto-staled by an agent-sourced contradiction: it is flagged for user review instead. Per-view mismatch never changes another session's validity. Head rechecks the same conditions immediately before promotion.

`memory.Recall` becomes scoped retrieval: eligible entries are `verified`, workspace-matched, safe, and current for that view; no candidate, retired or stale record enters ordinary prompts. Derive query from current user text/task title and description, explicitly known paths and symbols, not whole conversation. Require at least one exact path/symbol match or two distinctive keyword matches (one when only one distinctive query word exists); no fallback to unrelated memories. Rank deterministically: exact file +8, exact symbol +6, each distinctive keyword +1 (maximum 5); current evidence age under 30 days +1; ties: newest promotion, then ID ascending. No model-generated score or claimed verification affects rank. Cap at 4 entries and 300 estimated tokens per prompt, including heading, delimiters, title, IDs, content, and provenance labels; enforce against the *rendered combined block* using `ctxeng.Tokens`. Skip an entry that does not fit rather than truncating a command or evidence. Existing context selection may further reduce the block. Refresh/replace prior recalled items by stable IDs on every prompt, so old memories do not accumulate across turns; also remove entries when flag is disabled or validity changes. Respect `context.Scope.Memory` and existing scope exclusions, including probes.

The estimator is not an actual provider tokenizer: 300 is an estimated-token cap, not a hard billed-token cap, especially for Unicode/code. When a provider tokenizer is available use it; otherwise apply an independent 1200-byte serialized-block ceiling as well. Do not assume bytes or rune/4 guarantee provider-token count. Tests assert the defined estimator and byte cap, not a false exact provider-token guarantee. Stale entries can appear only in a clearly labeled review interface, never as verified prompt context. Label recalled content `Untrusted historical project observation; verify before use`; cite ID, observation time and evidence paths, and quote as data. Never let memory override user/system instructions or authorize tool calls.

## 6. Persistence, concurrency and migration

Use the existing `memory` table in the workspace catalog, with versioned JSON payload; no project file, separate index or parallel memory database. The catalog, including WAL/backups under its existing policy, is local workspace state and not committed to git. Workspace identity derives from the canonical existing configured workspace path, not git remote, email, or repository name; separate checkouts do not share memory. Store an opaque workspace ID, never the raw path, in new payloads and tombstones; migration must not duplicate a path containing email into memory. The existing catalog partition column currently holds a workspace path and requires privacy-safe migration too. Agent worktrees map explicitly to their parent configured workspace. Moving a workspace does not silently merge old partitions; provide explicit future migration, not automatic cross-repository sharing.

Catalog is the source of truth. Add revision and state columns/indexes to the existing table via transactional, idempotent `migrateCatalog`; keep payload version and columns consistent in the same transaction. Mutations use `UPDATE ... WHERE workspace=? AND id=? AND revision=?`, increment revision, and return `conflict` with current sanitized entry on mismatch. Candidate creation uses unique IDs and database constraints; a promotion and replacement retirement commit together. Explicit delete atomically replaces the entry with a content-free tombstone retaining only opaque ID, workspace partition, revision, deletion state and timestamp; it removes associated memory-only evidence and cannot be reused or restored. Tombstones have no automatic expiry, do not consume the candidate or permanent quota, and are excluded from UI lists and recall. Eliminate `persistLocked` memory snapshot upserts and restore-through-`Upsert`; otherwise stale processes can resurrect or overwrite changes. Each retrieval/review refreshes from catalog rather than trusting a process-local cache; notifications are hints, not synchronization. SQLite transactions/locking coordinate all Relo processes using the same catalog; retry bounded busy errors and return a visible failure, never fall back to blind overwrite. Reject writes when catalog is unavailable. Delete versus stale update returns conflict/not-found, never reinserts. List/query and snapshot are workspace-filtered, including delete and evidence lookup. User direct writes use the same transactional CAS and commit atomically with their `source: user` provenance and bumped revision; they are not queued and never pass through the candidate tables. No claim of coordination across different catalog paths or with older binaries that still perform snapshot writes.

Migration must precede any recall or mutation, in one transaction: legacy entries become `candidate` regardless of legacy `Verified`/score/source; keep stable safe ID and timestamps where valid, strip unsupported fields, validate all retained strings and scope. Legacy entries lack trustworthy structured provenance, so they cannot be permanent or recalled until fresh evidence and head approval. Unsafe or unclassifiable payloads must not be copied into new memory; scrub them from the active table and report only aggregate counts. Old database/WAL/backups may already contain sensitive legacy data; migration cannot honestly guarantee erasure from backups or SQLite pages. Document backup exposure and define secure data-removal handling before rollout; no existing erasure policy was verified. Do not create a new backup containing unsafe payloads. On malformed rows or transaction failure, roll back and disable memory capture/recall with a visible error rather than reverting to unsafe legacy behavior. Older binaries may ignore schema markers: a marker alone cannot enforce refusal. Before enabling, implement and test a database-level guard that rejects their legacy memory writes, or prove exclusive process ownership for the catalog; if neither works, block migration/rollout rather than claim compatibility. Do not silently destroy legacy data for rollback: retain only policy-compliant sanitized records, and require explicit user-managed backup/restore for rollback. Feature-off must not re-enable the old unsafe writer.

## 7. Poisoning and privacy defenses

- Intake is a strict bounded schema and allowlist, not raw reports. Limit title to 120 characters, body to 600, 8 paths, 8 symbols, 8 evidence references, and 4 KiB total serialized entry. Enforce limits after normalization and before any persistence, logs or notifications. Never truncate a rejected unsafe value into a seemingly safe value.
- Reject credential/token/private-key patterns, email addresses, secret-bearing keys, URLs with credentials or sensitive query parameters, command arguments likely to contain credentials, environment assignments, and content containing control characters or instruction-like role delimiters. Treat unknown/unclassifiable or high-entropy values as unsafe; show only a generic rejection reason. This is defense in depth, not a guarantee that a pattern scanner recognizes every secret: only structured allowlisted fields and verified references are eligible; reject anything whose safety cannot be established. Do not store raw evidence excerpts or arbitrary tool output. Apply the same checks to user edits, candidates, promotion rationale, filenames, metadata, notifications and logs. Never persist a rejected payload for debugging.
- Evidence reference IDs are opaque, workspace-bound, resolved by core from trusted records; a model cannot mint evidence or self-assert an outcome. Confirmation of existence does not prove semantic entailment; head must compare the claim against available trusted evidence. Run permission/security checks independently of memory. A command is an observation for human/agent consideration, never an executable instruction or permission grant.
- Encode/escape all values in webview HTML and prompt delimiters; never render HTML from memory. Require explicit confirmation for deletion, show the affected title safely, and never echo rejected secrets. Workspace boundaries, deterministic limits, revisions, head-only promotion and prompt labeling limit poisoning blast radius. Secrets already present in other systems' existing transcripts are outside memory storage; references must not expose them in memory UI or prompt.

## 8. Protocol, UI and settings

Extend `app/app.go` request handling and `docs/protocol.md`; `extension/src/protocol.ts` defines typed requests/results and `memory.updated` invalidation handling. Every request derives workspace and caller identity from trusted connection/session context, never a caller-provided workspace, role or state. Errors: `invalid_params`, `not_found`, `conflict`, `unsafe_content`, `evidence_unavailable`, `storage_unavailable`, `feature_disabled`. Responses and notifications are sanitized.

| RPC | Request → result | Rules |
|---|---|---|
| `memory.list` | optional `state`, `kind`, `cursor`, `limit` (max 100) → `{items,nextCursor}` | Workspace filtered; paginated stable ID order. Snapshot retains its existing array shape until clients migrate. |
| `memory.get` | `{id}` → entry | Includes safe provenance and current view validity. |
| `memory.propose` | `{kind,title,body,command?,scope,evidenceRefs}` → candidate | Core resolves evidence and applies intake; ignore/reject server-controlled fields. |
| `memory.update` | `{id,revision,patch}` → entry | Patch allowlisted fields; user direct write applies immediately as verified with `source: user` provenance, revised atomically; agent-originated edits create a linked candidate. Old arbitrary upsert semantics are removed behind protocol versioning. |
| `memory.requestReview` | `{id,revision}` → `{queued:true}` | Agent-originated candidates only, queued for next head turn; user writes never need it, and no promotion RPC is exposed to workers. |
| `memory.retire` | `{id,revision}` → entry | User or validated head action; immediate exclusion; agents cannot retire user-provenance entries. |
| `memory.delete` | `{id,revision}` → `{ok:true}` | User direct write: confirm in UI, payload deletion and content-free tombstone; no content in notification. |
| `context.promote` | existing `{agentId,itemId}` → entry | User direct write: promotes directly to verified with `source: user` provenance. Agent-side callers only propose a candidate. |

`memory.updated` emits `{id,revision,change}` after commit, with `change` including `deleted`; subscribers refetch and handle missing rows. Cross-process refresh on focus/prompt compensates for notifications being process-local. `extension/src/extension.ts` routes validated webview messages to core, handles errors/conflicts and refreshes lists; `extension/src/webview.ts` remains the message bridge. In `webview/src/main.js`, add a keyboard-accessible Memory section in the existing Context drawer with state/kind filters, search of the already-loaded safe page, titles, validity, evidence/commit/date and head rationale; use buttons for edit, promote, retire and delete, plus a review list of flagged agent contradictions. Explain that user edits apply immediately with user provenance and need no head approval, while agent proposals wait for the head. Use existing escaping helpers, accessible names, focus return and live error announcements. Never display raw evidence or secrets. For pagination/search do not claim a page-local search covers the full catalog.

Keep `relo.context.projectMemory` (`Settings.Memory`, default true) as the master switch: off blocks agent capture, head review/promotion and injection, but permits list, user direct edit, promote, retire and delete for user control. Add `relo.context.projectMemoryV2` default false as staged rollout flag in `extension/package.json`, `extension/src/extension.ts`, `orchestrator/coord.go`, `app/app.go:applySettings`, and the settings section in `webview/src/main.js`. With V2 off, disable unsafe legacy capture/recall/promotion, not silently fall back to the old pipeline; display that memory is paused. After migration/security gates and review, change default in a later rollout. Settings propagation must be tested on restart and live changes.

## 9. Phased implementation and acceptance tests

Each phase is a separately reviewable worker task; implementation follows approval. Nontrivial changes include runnable tests in the same phase. No phase should enable an unsafe half-pipeline.

**P1 — Safe catalog and migration.** Scope `core/internal/memory/store.go`, `core/internal/persistence/catalog.go`, `store.go`, `core/internal/app/app.go`, and corresponding Go tests. Add v2 schema, validated intake, workspace isolation, transactional CAS, content-free tombstones, safe legacy migration and old-writer refusal. Remove snapshot memory writes and restore merging. Tests: legacy verified→candidate; malformed/unsafe migration rollback and no leaked payloads; two catalog connections racing edits/promotion/delete with no resurrection; user direct write commits with `source: user` provenance and no candidate row; delete leaves a content-free tombstone; restart durability, workspace isolation, busy/failure behavior, quota protecting permanent entries, incompatible writer refusal. Until later phases, keep capture and recall disabled.

**P2 — Provenance and head promotion.** Scope `orchestrator/parse.go:Turn,RawReport`, `agent/agent.go:Report`, `orchestrator/worker.go`, `session.go`, `facts.go`, `prompt/prompt.go`, trusted execution/evidence adapters identified during implementation, `memory/store.go`, and their tests. ## 10. Risks and deliberately deferred work

Head judgment can be wrong, and evidence references/hashes establish provenance, not logical truth. Secret detection is imperfect; fail-closed intake reduces but cannot mathematically eliminate missed secrets. Old catalog pages, WAL and backups can contain historical sensitive data; secure erasure requires a separate storage-policy review. Provider token estimates are approximate. Toolchain/environment changes may escape fingerprints until the 30-day deadline. Unsaved-buffer state and trustworthy command observation may be unavailable; suppress rather than guess. Permanent records can exhaust storage: quota rejects rather than loses them. Git ancestor checks deliberately cause false staleness on rebases. Older concurrent binaries must be blocked before migration. No cross-repository sharing, automatic command execution, autonomous loop intervention, semantic embedding, or performance guarantee is proposed.
